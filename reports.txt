1. EXECUTIVE SUMMARY
================================================================================

BK Aggregator Parser is a sportsbook line ingestion and review system. It fetches
live/pre-match data from bookmaker APIs, normalizes it into a canonical Change[]
model, persists it in PostgreSQL (database: booker_adapter), and displays it in
a Next.js review dashboard.

Current phase scope (per WORKFLOW.md / README):
  - Parser adapters + CORE persistence + review frontend
  - Exactly TWO odds per match (main 2-way line; default factors 921 + 923)
  - Partner delivery (AMQP, multi-tenant HTTP API) is OUT OF SCOPE

Maturity assessment:
  - Phase A (Foundation): largely complete
  - Phase B (Fonbet adapter): partially complete — mapper/tests exist; poll loop
    still bypasses adapter stream and core ingestion
  - Phase C (Core ingestion): started — core/apply_changes.py exists and is used
    by Liga Stavok and Bet365, but NOT by Fonbet
  - Phases D–G (URN mapping, core API, frontend enhancements, multi-site UI):
    not started

The project has evolved beyond the README's "Fonbet-only" description. Three
bookmaker packages exist: fonbet, ligastavok, bet365.

CRITICAL GAP: backend/schema.sql and backend/scripts/create_database.sql are
referenced throughout docs and code but are NOT present in the repository
(not tracked by git, not on disk). Fresh clones cannot run setup without them.

================================================================================
2. PROJECT PURPOSE & BUSINESS CONTEXT
================================================================================

Goal:
  Build a reliable CORE layer that ingests bookmaker line data, stores canonical
  match/score/odds state, and provides a UI to validate parsing quality before
  building partner-facing delivery (RabbitMQ unified feed, HTTP API, etc.).

Full client specification (future phases):
  docs/TZ_bookmaker_parsing_COMPLETE_EN.md (gitignored locally, exists on disk)

Key design rule (target architecture):
  Adapters emit Change[]; CORE is the only writer to PostgreSQL.
  Adapters must NOT write SQL directly.

Odds scope constraint:
  Only 2 outcomes per match are ingested and displayed (e.g. Home/Away on main
  line). Full market trees (~1206 markets in Appendix C) are deferred.

4. HIGH-LEVEL ARCHITECTURE
================================================================================

Target data flow (from WORKFLOW.md):

  Bookmaker API/WS
       │
       ▼
  Adapter layer (per bookmaker: fonbet/, ligastavok/, bet365/)
       │  map packet → Change[] (fixture, score, betting_status, odds)
       ▼
  Core layer (backend/core/)
       │  apply changes idempotently to PostgreSQL
       ▼
  PostgreSQL (booker_adapter)
       │
       ▼
  Review frontend (Next.js)
       │  polls GET /api/matches every ~3.5–5s
       ▼
  Developer validates parsing quality

ACTUAL data flow today (varies by bookmaker):

  Fonbet:
    api.py → poll.py → fonbet/importer.py (legacy SQL) → PostgreSQL
    Adapter/mapper exists but poll path does NOT use it.

  Liga Stavok:
    adapter → mapper → Change[] → core/apply_changes.py → PostgreSQL

  Bet365:
    browser CDP tap → ZAP parse → Change[] → core/apply_changes.py → PostgreSQL

6. SHARED ADAPTER CONTRACT (backend/adapters/base.py)
================================================================================

Change types:
  - fixture        — match metadata (teams, league, start time, place)
  - score          — live score, timer, raw score breakdown
  - betting_status — blocked/unblocked/partial
  - odds           — market outcomes with factor_id and price

Key DTOs:
  - SportRef, TournamentRef, EventRef
  - OddsOutcome, OddsMarket
  - Change (change_type, match_payload_id, packet_version, payload)
  - HealthStatus, PacketSummary

BookmakerAdapter protocol methods:
  - discover_sports / discover_tournaments / discover_events
  - map_packet_to_changes
  - packet_summary
  - stream_live_changes
  - health

All three bookmaker adapters implement this contract (FonbetAdapter,
LigastavokAdapter, Bet365Adapter).

------------------------------------------------------------------------------
7.1 FONBET (backend/fonbet/) — Primary / most documented
------------------------------------------------------------------------------

API pattern:
  GET listLight?place=live&scopeMarket=1600  → full snapshot
  GET list?version={packetVersion}           → delta updates

Key modules:
  api.py       — HTTP fetch, packet_version extraction
  mapper.py    — JSON → Change[] (sports, events, scores, odds)
  adapter.py   — stream_live_changes, health metrics, resilient polling
  parsers.py   — sport tree resolution, line param normalization
  importer.py  — LEGACY direct SQL import (~660 lines, duplicates core logic)
  poll.py      — live loop; calls importer.import_packet() directly
  odds_config.py — enforces exactly 2 factor IDs (default 921, 923)
  sports_reference.py — Appendix A sport name resolution
  run_adapter.py — CLI adapter debug (no DB)
  test.json    — sample packet for offline testing

Strengths:
  - Clean mapper with unit tests (6 tests, all passing)
  - Two-odds filter implemented and tested (test_odds_at_most_two_per_match)
  - Resilient poll resets to listLight on error
  - Sports reference mapping with football display override

Gaps:
  - poll.py does NOT use FonbetAdapter.stream_live_changes_resilient()
  - poll.py does NOT use core/apply_changes.py
  - Duplicate persistence logic in importer.py vs core/apply_changes.py
  - No golden listLight fixture in fonbet/tests/fixtures/ (Phase B task)
  - schema.sql missing — setup cannot run on fresh clone

CLI:
  python main.py poll              (default Fonbet)
  python main.py import file.json
  python main.py adapter file.json
  python main.py adapter --live --once
  python main.py setup

Data flow:

Strengths:

  - Comprehensive tests (26 tests across api, mapper, config, browser, snapshot)
  - Well-documented README with CDP setup instructions
  - Paginated multi-sport live fetch (LIGASTAVOK_LIVE_ALL_SPORTS)

Gaps:

  - Requires manual Chrome CDP setup for reliable operation

CLI:

7.3 BET365 (backend/bet365/) — Experimental / browser-dependent
------------------------------------------------------------------------------

API pattern:
  wss://premws-pt1.365lpodds.com/zap/?uid={random}
  Proprietary ZAP binary/text protocol; requires pstk cookie + browser session

Key modules:
  adapter.py     — accumulates ZAP frames between poll ticks
  zap_parse.py   — protocol parser, fractional odds conversion
  state.py       — incremental feed state (ZapFeedState)
  browser_session.py — CDP Chrome frame tap
  cloudflare_gate.py — Cloudflare/Turnstile detection
  capture_session.py — auto-capture uid + cookie from browser
  listen.py      — debug WebSocket listener
  mapper.py      — state → Change[]

Data flow:
  Browser CDP tap → ZAP frames → state → Change[] → core/apply_changes.py

Strengths:
  - 17 unit tests, all passing (protocol parse, Cloudflare gate, multi-sport)
  - Safe mode with configurable recovery/reload behavior
  - Maps tennis 2-way and soccer 1X2 to normalized 921/923 factor slots
  - Cloudflare wait/auto-click support

Gaps:
  - Fully dependent on live browser session (fragile for automation)
  - Not suitable for headless server deployment without CDP Chrome
  - Separate Chrome port (9223) from Liga Stavok (9222)
  - bet365/tests/ lacks __init__.py — not discovered by `unittest discover -s .`
  - Most complex operational setup of the three adapters

CLI:
  python main.py poll bet365
  python main.py listen bet365 [--browser] [--seconds N]
  python main.py capture bet365 [--env]

8. CORE LAYER (backend/core/)
================================================================================

Current state: MINIMAL — single module apply_changes.py (~348 lines)

What it does:
  - Groups Change[] by match_payload_id
  - Upserts: sites, countries, sports, leagues, matches
  - Upserts: match_scores, betting_status, odds_lines
  - Normalizes Liga Stavok factor IDs to 921/923 slots for frontend compatibility
  - Prunes old snapshots and stale matches via retention.py
  - Records import_snapshots audit row per tick

What is missing (per WORKFLOW Phase C–E):
  - core/ingest.py orchestrator
  - core/handlers/ per ChangeType (fixture, score, betting_status, odds)
  - core/models.py
  - core/tests/ (idempotency, max-2-odds enforcement at DB level)
  - core/api/ read-only HTTP API for frontend
  - URN assignment (sr:match:*, sr:sport:N)
  - factor_id → market_id mapping
  - urn_map table

Technical debt:
  - apply_changes.py imports from fonbet.parsers (couples core to Fonbet)
  - Fonbet poll path still uses fonbet/importer.py instead of core
  - Two parallel write paths with duplicated upsert SQL

20. CONCLUSION
================================================================================

BK Aggregator Parser is a well-structured, actively developed bookmaker line
ingestion system with a clear architectural vision (adapter → Change[] → core →
DB → review UI). The shared adapter contract is solid, and the project has
already expanded to three bookmakers with meaningful test coverage.

The main gaps are:
  (1) missing database schema in version control,
  (2) incomplete migration from legacy Fonbet importer to core ingestion,
  (3) frontend and docs ahead/behind git tracking,
  (4) operational complexity for browser-dependent adapters.

For a detailed code review session, start with the adapter contract, compare
fonbet/importer.py vs core/apply_changes.py side by side, then trace one poll
tick through ligastavok (the cleanest path) and the frontend queries that
render the result.
